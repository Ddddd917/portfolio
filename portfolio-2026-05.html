Project 01 · Architecture

ORION · Personal Intelligence System Design stage

ORION · 个人智能系统 设计阶段

A local-first personal AI system — not a better chatbot, but intelligent infrastructure that actually knows me.

本地优先的个人 AI 系统——不是一个更好的聊天机器人，而是一个真正了解我的智能基础设施。

ORION — the name comes from the Orion constellation, evoking a sense of direction and a systematic approach. It expands to Orchestrated Reasoning and Intelligence Operating Network, which defines the system's core traits: orchestrated reasoning, intelligent operation, and networked collaboration.

ORION——名字来自猎户星座，寓意方向感与系统性。展开为 Orchestrated Reasoning and Intelligence Operating Network，定义了系统的核心特征：编排式推理、智能化运作、网络化协同。

Two parallel motivations drove the design of ORION. The first is personalized capability: OpenClaw proved that an AI agent can get things done, but it is generic — every conversation starts with re-explaining the background, and it does not know my projects, my files, or my preferences. What I want is a personal AI system that holds my full context and can make targeted judgments instead of giving generic answers. The second is digital asset management: my files are scattered across multiple devices and platforms, naming is inconsistent, and from time to time I cannot find what I need. Organizing them by hand the traditional way would take a great deal of time, but AI makes it possible to solve this problem systematically.

设计 ORION 有两个并行的动机。第一是能力个性化：OpenClaw 证明了 AI Agent 能做事，但它是通用的——每次对话都要重新解释背景，不了解我的项目、我的文件、我的偏好。我想要的是一个了解我全部上下文的个人 AI 系统，能做出有针对性的判断而不是通用的回答。第二是数字资产管理：文件分散在多个设备和平台，命名不规范，找不到的情况时有发生。按传统方式手动整理需要耗费大量时间，但 AI 让系统性地解决这个问题变得可能了。

ORION's goal in one sentence: turn AI from a general-purpose tool into personal infrastructure.

一句话概括 ORION 的目标：让 AI 从通用工具变成个人基础设施。

Key product decisions

核心产品决策

Why three different databases?
为什么用三种数据库？
Different kinds of data have different optimal retrieval methods. “Accuracy on the Avatr project” → semantic search (ChromaDB); “the highest-rated movie” → structured query (SQLite); “who among the people I know works in AI” → graph query (Neo4j). Multi-model storage directly affects the accuracy and coverage of the answers.
不同数据有不同的最佳检索方式。「阿维塔项目准确率」→ 语义检索（ChromaDB）；「评分最高的电影」→ 结构化查询（SQLite）；「认识的人里谁做 AI」→ 图查询（Neo4j）。多模态存储直接影响回答的准确性和覆盖面。
Why an LLM Router?
为什么需要 LLM Router？
“Today's weather” gets an answer from the 8B model in 0.5 s; “analyze my interview strategy” needs a 32B model or even cloud-hosted Claude. The routing policy determines the response speed users perceive and the quality of the answers — the core trade-off of the cost–quality–latency triangle in AI products.
「今天天气」用 8B 模型 0.5s 出结果；「分析面试策略」需要 32B 甚至云端 Claude。路由策略决定用户感知的响应速度和回答质量——AI 产品中「成本-质量-延迟」三角的核心权衡。
Why voice as the primary interaction mode?
为什么以语音作为主交互模式？
ORION's core use case is not typing at a computer; it is triggering the system at any moment in daily life — asking a question while cooking, capturing an idea while walking, checking the schedule before heading out. Voice is the lowest-friction way to interact in those situations. The system's input and output are therefore both designed around voice: Whisper for speech-to-text, Edge TTS for speech synthesis, and a DJI Mic Mini to ensure audio pickup quality (STT accuracy depends heavily on the audio signal-to-noise ratio). The goal is an experience closer to “talking with someone who knows you” than to “opening an app and typing a command.”
ORION 的核心使用场景不是坐在电脑前打字，而是在日常生活中随时触发——做饭时问一个问题、走路时录入一条想法、出门前确认日程。语音是这些场景下摩擦最低的交互方式。因此系统的输入输出都围绕语音设计：Whisper 做语音转文字，Edge TTS 做语音合成，DJI Mic Mini 保证拾音质量（STT 的准确率高度依赖音频信噪比）。目标是让交互体验接近「和一个了解你的人对话」，而不是「打开一个 App 输入指令」。

Key product decisions

核心产品决策

Why refactor from a single page into a multi-page app?
为什么从单页重构为多页应用？
Phase 2 testing showed that document analysis is only the entry point; managing documents after they are ingested is the core use case. Going from one page to 10 (Dashboard + Upload + 8 knowledge domains) meant an architectural refactor involving 4 new core modules.
Phase 2 测试后发现，文档分析只是入口，入库后的管理才是核心使用场景。从单页改为 10 个页面（Dashboard + 上传 + 8 个知识域），涉及 4 个新核心模块的架构重构。
Why operate directly on local files?
为什么做本地文件直接操作？
The tool does more than analyze documents: it renames, moves, and archives local files directly, which is more intuitive than doing it by hand in Finder and keeps the folder structure of the ORION knowledge base consistently clean. But file operations carry the risk of being irreversible, so every operation runs only after the user confirms it: the AI proposes, the human calibrates. Deletion has an additional checkbox safety switch to prevent accidental removal.
这个工具不只是分析文档，而是直接对本地文件执行重命名、移动、归档——比在 Finder 里手动操作更直观，也让 ORION 知识库的文件夹结构始终保持清晰。但文件操作有不可逆风险，所以所有操作都需要用户确认后才执行：AI 出建议，人来校准。删除操作额外加了 checkbox 安全开关防误删。
Why design 8 knowledge domains rather than more or fewer?
为什么设计 8 个知识域而不是更多或更少？
Too many makes classification fuzzy; too few overloads some domains with documents. These 8 cover the main categories of everyday documents; each domain carries a 0-1 confidence score, and the design separates a primary domain from related domains.
太多导致分类模糊，太少导致某些域文档过多。8 个覆盖了日常文档的主要类别，每个域附带 0-1 的置信度分数，支持主域 / 关联域分离。

Project 03

Resume Copilot Live

Resume Copilot 已上线

After applying to jobs in bulk during my summer job search, judging job description (JD) fit and tracking application progress became the efficiency bottleneck. This tool uses AI to run the resume-match analysis automatically and provides a board for managing application progress.

暑期求职批量投递后，JD 匹配判断和投递进度管理成了效率瓶颈。这个工具让 AI 自动完成简历匹配分析，并提供投递进度管理看板。

Python Streamlit Zhipu GLM API 智谱 GLM API Claude Code

GitHub · github.com/Ddddd917/personal_resume_analyzer

After applying to jobs in bulk during my summer job search, two problems surfaced. First, reading JDs one by one to judge fit was too slow: just deciding “is this position worth applying to?” took over ten minutes. Second, my application records were scattered, so I could neither track progress nor review outcomes. The goal of this tool is to automate this chain: read the JD → judge the match → manage the application.

暑期求职阶段批量投递后，两个问题浮出水面：一是逐条阅读 JD 判断匹配度效率太低，光是「这个岗位值不值得投」就要花十几分钟；二是投递记录分散，无法追踪进度和复盘结果。这个工具的目标是把「读 JD → 判断匹配 → 投递管理」这条链路自动化。

Uploading a resume automatically builds a candidate profile whose data structure is aligned to the Feishu (Lark) HR system; after a JD is pasted in, the AI runs a three-dimensional match analysis (hard requirements 40%, experience match 35%, soft-criteria match 25%) and outputs a match score, an item-by-item gap diagnosis, and tailored resume-optimization suggestions. Analysis results are saved automatically to the application board, giving a complete workflow from JD parsing to match analysis to the application decision.

上传简历后自动构建个人画像（数据结构对齐飞书 HR 系统），粘贴岗位 JD 后 AI 完成三维匹配分析（硬性条件 40%、经验匹配 35%、软性匹配 25%），输出匹配度评分、逐条差距诊断和定制化简历优化建议。分析结果自动保存到投递看板，实现从 JD 解析到匹配分析到投递决策的完整工作流。

Key product decisions

核心产品决策

Why align the candidate profile's data structure with the Feishu HR system?
为什么个人画像数据结构要对齐飞书 HR 系统？
I noticed that most of my target companies (ByteDance, Zhipu AI, Xiaomi, and others) manage their hiring pipeline in the Feishu HR system. Rather than design my own profile schema, I aligned it directly with Feishu HR's field standard (basic information, plus multiple entries each for education, internships, and projects). That way, when the AI runs a match analysis, the dimensions it compares against are the same ones HR actually looks at when screening resumes. This was a product decision, not a technical one: it starts from the user's actual use case.
观察到目标公司（字节、智谱、小米等）大多使用飞书 HR 系统管理招聘流程。与其自己设计一套画像结构，不如直接对齐飞书 HR 的字段标准（基础信息、教育经历 × 多段、实习经历 × 多段、项目经历 × 多段）。这样 AI 做匹配分析时，对照的维度和 HR 实际筛选简历时看的维度是一致的。这不是技术决策，是产品决策——从用户实际场景出发。
Why a three-dimensional score instead of a single match score?
为什么用三维评分而不是单一匹配分数？
A single score hides where the weak spot is. The three dimensions are hard requirements (40%), experience match (35%), and soft-criteria match (25%). Hard requirements are the threshold: if you do not meet them there is no point applying, so they carry the highest weight; soft-criteria match is the hardest to quantify, so it carries the lowest. What an interviewer cares about is not the total score but the gap diagnosis: whether the shortfall is in education, experience, or soft skills.
单一分数掩盖了短板在哪里。三维拆分为硬性条件（40%）、经验匹配（35%）、软性匹配（25%）——硬性条件是门槛，不达标就不用投，所以权重最高；软性匹配最难量化，所以权重最低。面试官看重的不是总分，而是差距诊断：到底差在学历、经验、还是软性能力上。
Why build an application board rather than just the analysis?
为什么要做投递看板而不是只做分析？
An analysis is a one-off action, but a job search is an ongoing process. After applying in bulk, I needed to track each position's status (not applied / applied / replied / interviewing / passed / rejected), sort by match score to set priorities, and review which types of positions converted better. The board strings the one-off analyses together into a manageable workflow.
分析是单次行为，但求职是持续过程。批量投递后，需要追踪每个岗位的状态（未投递 / 已投递 / 已回复 / 面试中 / 已通过 / 已拒绝），按匹配度排序决定优先级，复盘哪些类型的岗位转化率更高。看板把单次分析串成了可管理的工作流。
Match analysis — three-dimensional score (hard 40% / experience 35% / soft 25%) and gap diagnosis
匹配分析 — 三维评分（硬性 40% / 经验 35% / 软性 25%）与差距诊断
Application board — sorted by match score, with status tracking and expandable detailed analysis
投递看板 — 按匹配度排序、状态追踪、详细分析可展开
Lesson learned
During development I hit a silent API failure: the model name was misspelled (product name glm-4.7-flashx vs. API parameter glm-4-flashx), but the API raised no error and the page just kept spinning. Debugging it took many wrong turns. The product lesson: failures in an AI product must be visible; a silent failure is the worst user experience.
开发教训
开发中遇到 API 静默失败——模型名拼写错误（产品名 glm-4.7-flashx vs API 参数 glm-4-flashx），但 API 无报错提示，页面一直转圈。排查走了很多弯路。产品启示：AI 产品的失败必须可见，静默失败是最差的用户体验。

Reflections

Vibe Coding and AI product thinking

Vibe Coding 与 AI 产品思考

Methodology and insights distilled from hands-on work on four projects plus systematic study at Anthropic Academy.

四个项目的实践 + Anthropic Academy 的系统学习，沉淀出的方法论和认知。

Vibe Coding methodology
Vibe Coding is not “having AI write the code”; it is “driving AI development with product thinking.” Across four projects, my core value came down to three things. First, defining what to build and what not to build — for example, the Document Ingestion Assistant skipped the export feature to prioritize file management, and Resume Copilot aligned its profile structure with Feishu (Lark) HR instead of designing its own. Second, making architecture decisions — for example, storing metadata separately from the files, placing the knowledge base under the user's Documents directory rather than the project directory, and scoring on three dimensions instead of a single match score. Third, root-cause analysis in testing — discovering that the naming scheme lacked a document-type dimension, and that a silent API failure was caused by a misspelled model name; in each case I spotted the problem while testing, traced the cause, and gave the AI a new prompt to fix it.
Vibe Coding 方法论
Vibe Coding 不是「让 AI 写代码」，而是「用产品思维驱动 AI 开发」。四个项目做下来，我的核心价值归结为三件事：第一，定义做什么和不做什么——比如入库助手决定跳过导出功能优先做文件管理，Resume Copilot 决定画像结构对齐飞书 HR 而非自己设计；第二，做架构决策——比如元数据与文件分离存储、知识库路径放在用户文档目录而非项目目录、三维评分而非单一匹配分数；第三，测试归因——发现命名缺少文档类型维度、API 静默失败的根因是模型名拼写错误，都是我在测试中识别问题后定位原因并给 AI 新 Prompt 修复的。

Three insights from studying AI products

学习 AI 产品的三个认知

Start with a simple solution; add complexity only when it proves necessary
从简单方案开始，只在证明必要时增加复杂度
Anthropic's core advice in “Building Effective Agents” is to “find the simplest solution possible.” That principle runs through the technology choices in every one of my projects: the Document Ingestion Assistant uses Streamlit instead of React and local JSON instead of a database; ORION's architecture is a hybrid — everyday queries take a lightweight Routing path for fast responses, structured tasks run as Workflows for stability, and only complex tasks that genuinely require dynamic decision-making switch to Agent mode. More complexity is not better; just enough is best.
Anthropic 在《Building Effective Agents》中的核心建议是 "find the simplest solution possible"。这个原则贯穿了我所有项目的技术选型：入库助手用 Streamlit 而不是 React，用本地 JSON 而不是数据库；ORION 的架构设计是混合式的——日常查询走轻量 Routing 快速响应，结构化任务走 Workflow 保证稳定性，只有真正需要动态决策的复杂任务才启动 Agent 模式。不是越复杂越好，而是刚好够用最好。
The core design challenge of AI products is non-determinism
AI 产品的核心设计挑战是非确定性
In traditional software, the same input always produces the same output. In an Agent system, every decision the LLM makes is probabilistic — the same input can take different paths. That means bugs are hard to reproduce, costs are hard to predict, and users cannot anticipate how the system will behave. The silent API failure I ran into while building Resume Copilot is a case in point: a misspelled model name raised no error — it simply hung silently — and debugging it took many detours. For product design, this demands two things — transparency (let users see what the AI is doing) and controllability (critical actions must be confirmed by a human). The Document Ingestion Assistant's “AI proposes, the human calibrates” is that principle in practice.
传统软件同样的输入一定产出同样的结果，但 Agent 系统中 LLM 的每一步决策都是概率性的——同样的输入可能走不同的路径。这意味着 Bug 难复现、成本难预测、用户无法预期系统行为。我在 Resume Copilot 开发中遇到的 API 静默失败就是一个缩影：模型名拼写错误不会报错，只会静默挂起，排查走了很多弯路。产品设计上，这要求两件事——透明度（让用户看到 AI 在做什么）和可控性（关键操作必须人工确认）。入库助手的「AI 出建议，人来校准」就是这个原则的体现。
The core skill of an AI Product Manager is judgment, not coding
AI 产品经理的核心能力是判断力，不是编码能力
Vibe Coding proved one thing: AI can generate the code, but the judgment calls — what to build, what not to build, and how far to take it — cannot be automated. Which feature to cut (removing the interview-tracking module), whose data structure to align with (the Feishu HR system), how to split the architecture (refactoring a single page into multiple pages), where to sit on the Agent spectrum (ORION's hybrid architecture) — these product decisions are the irreplaceable value a PM brings. Technology is changing ever faster, but there is no shortcut to building judgment.
Vibe Coding 证明了一件事：代码可以由 AI 生成，但「做什么、不做什么、做到什么程度」这些判断无法自动化。哪个功能该砍（删除面试追踪模块）、数据结构该对齐谁（飞书 HR 系统）、架构该怎么拆（单页重构为多页）、在 Agent 光谱上该站在哪个位置（ORION 的混合架构）——这些产品决策是 PM 不可替代的价值。技术在加速变化，但判断力的积累没有捷径。
